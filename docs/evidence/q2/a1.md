# Q2 — 3-environment architecture evolution

## Per-environment component table

| Component | Dev | Stage | Prod | Rationale for changes |
|---|---|---|---|---|
| **LobeChat** | `t3.medium` EC2, Docker Compose, HTTP on port 47000 | `t3.large` EC2, Docker Compose, HTTPS via Caddy + sslip.io | ECS Fargate (2 vCPU / 4 GB), ALB + ACM cert, auto-scaling 1–4 tasks | Dev: fast iteration, no SSL overhead. | **MinIO** | Docker container, local volume | Docker container, EBS volume | **AWS S3** (native), LobeChat `S3_ENDPOINT` removed, `AWS_ACCESS_KEY_ID` via IAM role | Prod: S3 eliminates MinIO ops burden, 11 nines durability, no capacity planning |
| **Qdrant** | `t3.medium` EC2, Docker container, local volume | `t3.large` EC2, Docker container, EBS `gp3` 50 GB | `r7g.xlarge` EC2 (memory-optimised), EBS `gp3` 500 GB, daily EBS snapshots | Hard constraint: Qdrant on EC2 in all envs — see dedicated section below |

| **LLM / vLLM** | OpenRouter API (no local GPU needed) | OpenRouter API | OpenRouter API (primary) + **AWS Bedrock** (fallback/compliance) | vLLM requires GPU → cost-prohibitive for dev/stage. Bedrock in prod gives EU data residency guarantees and SOC2 audit trail |

## Qdrant on EC2 — sizing, snapshots, recovery

Qdrant is kept on EC2 in all three environments because:
1. No AWS-managed vector DB exists in `eu-west-1` with equivalent capabilities (Pinecone is US-only; OpenSearch k-NN is significantly slower at >1M vectors; pgvector on RDS lacks HNSW indexing at scale).
2. Qdrant's memory-mapped storage model benefits from direct EBS access — a containerised Fargate task with EFS would add latency and cost.

**Sizing per environment:**

| Env | Instance | EBS | Justification |
|---|---|---|---|
| Dev | `t3.medium` (4 GB RAM) | `gp3` 20 GB | < 100k vectors, single developer, acceptable restart time |
| Stage | `t3.large` (8 GB RAM) | `gp3` 50 GB | Production-sized anonymised corpus subset (10–20% of prod data) |
| Prod | `r7g.xlarge` (32 GB RAM) | `gp3` 500 GB | 3–5M vectors for full legal corpus; memory-mapped segments fit in RAM to avoid page faults on hot queries |

**Snapshot policy (prod):**
- Daily EBS snapshot at 02:00 UTC via AWS Data Lifecycle Manager, retention 30 days.
- Weekly snapshot retained 12 weeks (for point-in-time rollback after a bad indexing run).
- Qdrant snapshot API (`POST /collections/{name}/snapshots`) triggered before any bulk re-index, stored to S3 via `aws s3 cp`.

**Instance recovery:**
1. CloudWatch alarm on `StatusCheckFailed_Instance` → SNS → Lambda → creates replacement EC2 from latest EBS snapshot.
2. Target recovery time: < 15 minutes (snapshot restore + Docker start).
3. LobeChat and MCPHub tolerate Qdrant unavailability gracefully — RAG queries return empty results, non-RAG chat continues unaffected.

## AWS managed services in prod (≥ 4)

1. **RDS Postgres 16** (`db.r7g.large`, Multi-AZ) — replaces Docker Postgres. Automated backups, read replica for analytics queries, pgvector extension supported.
2. **S3** — replaces MinIO. `lobe` bucket for file uploads, `qdrant-snapshots` bucket for vector DB backups, `hayhooks-pipelines` bucket for pipeline YAML storage.
3. **ALB + ACM** — terminates HTTPS with AWS-managed certificate (auto-renewed), routes `/api/*` to LobeChat Fargate tasks, `/casdoor/*` to Casdoor tasks, health checks on `/api/health`.
4. **AWS Secrets Manager** — stores `KEY_VAULTS_SECRET`, `NEXT_AUTH_SECRET`, `POSTGRES_PASSWORD`, `OPENROUTER_API_KEY`, `AUTH_CASDOOR_SECRET`. ECS task role has `secretsmanager:GetSecretValue` permission; secrets injected as env vars at task start.
5. **CloudWatch** — container logs via `awslogs` driver, custom metrics (active sessions, MCP tool call latency, Qdrant query p99), alarms on error rate > 1% and p99 > 3s.
6. **Route 53** — hosted zone for production domain, A record pointing at ALB, health check with failover routing.

## Promotion flow

```
feature/* ──► dev branch ──► PR review ──► stage branch ──► manual approval ──► main (prod)
                                              ↓
                                     GitHub Actions CI:
                                     - docker build + push to ECR
                                     - run db migrations (dbmate)
                                     - smoke test: curl /api/health
                                     - Qdrant collection integrity check
```

**Branching:**
- `dev` branch: auto-deploys to dev EC2 on push via GitHub Actions (`docker compose up -d`).
- `stage` branch: auto-deploys to stage EC2 on merge from `dev`. Runs full integration test suite (Playwright against staging URL).
- `main` branch: deploys to prod only after manual approval in GitHub Actions environment (`prod` environment requires 1 approver).

**Tagging:** Semantic versioning via Commitizen (`cz bump`). Every prod deployment tagged `vX.Y.Z`. Rollback = re-deploy previous tag.

**Config promotion:** `.env` files are not in git. Per-environment secrets live in Secrets Manager. Promotions carry code, not secrets — secrets are environment-specific and never cross boundaries.

## Data strategy

**Dev — realistic-but-safe data:**
- Postgres: anonymised dump of stage DB, generated monthly with `pg_dump | anonymise.py` (replaces PII with synthetic equivalents using `faker`).
- Qdrant: 5% random sample of prod corpus, re-embedded in dev (ensures embeddings are representative without exposing full client data).
- MinIO/S3: synthetic PDF documents generated from templates — never real client files.

**Stage — mirrors prod:**
- Postgres: refreshed weekly from prod RDS snapshot, run through anonymisation pipeline.
- Qdrant: full copy of prod collection (data is already abstracted as vectors; source documents not in stage).
- S3: empty bucket, populated by stage integration tests.

**Prod — backup and restore:**
- RDS: automated daily snapshots, 35-day retention. Point-in-time recovery to any second within retention window.
- S3: versioning enabled on `lobe` bucket, lifecycle rule moves versions > 30 days to Glacier.
- Qdrant: EBS snapshot daily (see above). Full restore tested quarterly via GameDay exercise.
- Recovery objective: RPO 24h (acceptable for a legal knowledge base — no real-time transactions), RTO 15 min for Qdrant, < 5 min for ECS tasks (new task starts from existing container image).

## Trade-off table

| Dimension | Dev | Stage | Prod |
|---|---|---|---|
| **Reliability** | ⭐⭐ Low — single EC2, no HA, restarts accepted | ⭐⭐⭐ Medium — EBS-backed volumes, automated smoke tests | ⭐⭐⭐⭐⭐ High — Multi-AZ RDS, ECS auto-scaling, ALB health checks, CloudWatch alarms |
| **Cost** | ⭐⭐⭐⭐⭐ ~$80/mo (t3.medium + minimal EBS) | ⭐⭐⭐⭐ ~$250/mo (t3.large + EBS + OpenRouter test budget) | ⭐⭐ ~$800–1,200/mo at 100 MAU (see Q3) |
| **Ops complexity** | ⭐⭐⭐⭐⭐ Minimal — `docker compose up`, SSH access, no drift detection | ⭐⭐⭐ Medium — CI/CD pipeline, migration scripts, integration tests | ⭐⭐ High — ECS task definitions, IAM roles, Secrets Manager rotation, CloudWatch dashboards, GameDay exercises |

The trade-off is intentional: ops complexity is front-loaded into prod where it buys reliability. Dev is deliberately simple so engineers iterate fast without fighting infrastructure.

## Reverse-proxy / TLS choice

**Dev:** No TLS. LobeChat on `http://localhost:47000`. Casdoor configured with `http` redirect URIs. Acceptable because dev is single-machine, no cross-origin requests.

**Stage:** Caddy on the EC2, sslip.io domain (`<ip>.sslip.io`), ZeroSSL certificate via ACME HTTP-01. Chosen because: zero domain purchase required, certificate auto-renews, and sslip.io DNS resolution is automatic from the IP — no DNS management overhead. This is the exact setup deployed for this project (validated: `curl -sI https://108.130.141.156.sslip.io/` returns `HTTP/2 307 via Caddy`).

**Prod:** ALB with ACM certificate on a Route 53 domain. ALB chosen over EC2-hosted Caddy because: (a) ALB health checks enable zero-downtime ECS deployments; (b) ACM auto-renews without any agent on the instance; (c) ALB access logs ship to S3 for compliance audit; (d) WAF can be attached to the ALB for layer-7 filtering without touching application code.
